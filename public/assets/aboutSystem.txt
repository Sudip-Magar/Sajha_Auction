1. WHAT THE SYSTEM IS
=====================================================================
Sajha Auction is a Nepal-focused marketplace for SECOND-HAND products.
Items are sold in two ways:
   - DIRECT SELL  : fixed (or negotiable) price. Buyer orders, meets
                    the seller in person, inspects, pays CASH.
   - AUCTION      : live bidding (manual and proxy bids). The highest
                    valid bid wins. The winner pays at least a minimum
                    deposit online (eSewa, sandbox - the buyer may
                    choose to pay more) and the rest in cash at the
                    meetup.

There are three kinds of people:
   - GUEST   : can browse products and auctions and use the AI guide.
   - USER    : registers (email OTP or Google), can buy, bid (if
               approved for auctions), chat, wishlist, cart, orders.
   - SELLER  : a user approved by an admin; can list products/auctions.
   - ADMIN   : a separate login; approves sellers, auction access and
               listings; manages users, categories, FAQs, orders and
               settings.

Everything is real time: live bids, chat and notifications update
without refreshing (Laravel Reverb WebSockets).

There is also an AI assistant (Google Gemini) that explains how the
site works.

2. HOW A REQUEST TRAVELS THROUGH THE SYSTEM
=====================================================================
The project is a Laravel application where almost every PAGE is a
LIVEWIRE COMPONENT (a PHP class + a Blade view).

   Browser asks for  /auction/5
        |
   routes/web.php  finds the route:
        Route::get('/auction/{auction}', AuctionDetail::class)
        |
   MIDDLEWARE runs first (here: 'user' = must be logged in and active)
        |
   The Livewire component class  App\Livewire\User\AuctionDetail
        - mount()  loads data (models) from the database
        - render() returns the Blade view
             resources/views/livewire/user/auction-detail.blade.php
        |
   HTML is sent to the browser. From now on the page "talks" to PHP
   through Livewire:
        - a button with wire:click="placeBid" calls the PHP method
          placeBid() (an AJAX request to /livewire/update)
        - PHP changes the database (through MODELS and SERVICES)
        - PHP may fire EVENTS / NOTIFICATIONS
        - Livewire re-draws only the parts that changed
        |
   Real-time: events are broadcast through Laravel Reverb; the browser
   (Laravel Echo) hears them and asks Livewire to refresh.

The layers, from top to bottom:
   Blade views (what you see)  ->  Livewire components (page logic)
   ->  Services (business rules, e.g. the auction engine)
   ->  Models (database access)  ->  MySQL database
   Side channels: Events + Notifications + Mail + Reverb (real time),
   Scheduler (auctions ending).

5. THE DATABASE (EVERY TABLE)
=====================================================================
"FK" = foreign key (a link to a row in another table).

---- PEOPLE ------------------------------------------------------
users
   Every normal account. Columns: id, google_id (unique), name, email
   (must be unique: enforced by the sign-up validation, not by a
   database constraint), username (unique), phone, date_of_birth_en (AD date),
   daate_of_birth_np (B.S. date; the spelling "daate" is in the real
   column name), gender ('male'|'female'|'other'), bio, avatar,
   password (hashed), is_verified, is_seller, seller_application_pending,
   is_auction_allowed, status ('active'|'inactive'), timestamps.
   The three yes/no flags are the "roles":
       is_seller           -> may list products
       is_auction_allowed  -> may bid and host auctions
       seller_application_pending -> asked to become a seller, waiting
admins
   Separate accounts for the admin panel (own login guard). Columns:
   name, email, phone, role, position, date_of_joining, gender,
   password, avatar, address, status.
document_images
   Identity documents a user uploads to apply for AUCTION access.
   user_id FK, type (citizenship_front/back, passport, driving_license,
   national_id, other), image path, is_approved, is_rejected.
password_reset_tokens, sessions
   Standard Laravel tables (sessions store logins because the session
   driver is "database").

---- CATALOGUE ---------------------------------------------------
categories
   Top-level categories: name, slug, description, image, icon, color,
   status, sort_order.
sub_categories
   Children of a category: category_id FK + the same fields. A product
   belongs to a SUB-category.
products
   Every listing (direct-sell or auction). sku, name, slug,
   seller_id FK->users, sub_category_id FK->sub_categories, description,
   specifications, condition, usage_duration, purchase_date, quantity,
   retail_price (original price), sale_price (direct-sell price),
   negotiable, listing_type ('direct_seller'|'auction'), approval_status
   (pending|approved|rejected|correction - replaced the old is_approved
   boolean, see section 6), remarks (admin's note when rejecting or
   requesting a correction), is_featured, is_trending, views_count,
   location, meetup_location, meetup_instructions, delivery_available
   (no longer used), expires_at, status ('pending'|'active'|'sold').
product_images
   Photos: product_id FK, path, image_type ('general'|'proof' -
   proof = warranty card etc. shown only to admins), sort_order.
product_timelines
   A history log per product: event_type, title, description, actor_id
   (who did it). Written on upload, approval, order, cancellation...
wishlists          user_id + product_id (saved items)
cart_items         user_id + product_id + quantity
faq_categories     name, slug, sort_order
faqs               faq_category_id, question, answer, sort_order,
                   is_active (managed by admin)
subscribers        newsletter emails from the footer
settings           key / value / group (admin site settings such as
                   site name, social links, security options)

---- AUCTIONS ----------------------------------------------------
auctions
   One per auction product. product_id FK, auction_type,
   start_time/end_time (+ the B.S. text versions start_time_np,
   end_time_np), extended_end_time (set by anti-sniping),
   current_price, total_bids, winner_id FK->users (nullable),
   winning_price, settlement_reason, status
   ('pending' -> 'active' -> 'completed' | 'ended_unsold').
traditional_auctions
   The rule set of a traditional auction: auction_id FK,
   starting_bid, reserve_price (secret minimum), min_bid_increment,
   timer_start_seconds, timer_reset_seconds (anti-sniping window).
bids
   Every bid: auction_id FK, bidder_id FK->users, bid_amount,
   max_proxy_amount (secret maximum for proxy bids), is_proxy,
   ip_address, placed_at (time).

---- ORDERS ------------------------------------------------------
orders
   One order per seller per checkout, and one per won auction.
   order_number (ORD-YYYYMMDD-XXXXX), buyer_id, seller_id,
   auction_id (only for auction orders), status
   ('pending'|'confirmed'|'meetup_scheduled'|'completed'|'cancelled'),
   total_amount, deposit_amount (the MINIMUM online payment, not the
   only amount that can be paid - see payment_transactions below),
   deposit_status (native enum OrderDepositStatus: not_required|
   pending|paid|failed|refund_owed|forfeited), deposit_transaction_uuid
   (the uuid of the latest eSewa attempt), payment_method, payment_status
   (native enum OrderPaymentStatus: pending|paid|refunded), handover_type,
   meetup_location, meetup_time (date+time in AD), meetup_time_np
   (the same date in B.S. text), shipping_address (old, unused),
   buyer_phone, notes, cancellation_reason_category (native enum
   OrderCancellationReason, section 8), cancellation_note,
   complaint_status (native enum OrderComplaintStatus: null|
   under_review|confirmed_damaged|not_damaged - a Group 2 buyer
   complaint's admin-review state), complaint_resolution_note (the
   admin's note on the verdict), stale_notified_at (reserved for a
   not-yet-built "stale order" admin check, see aboutSystem.txt section
   21 / newUpate.txt Part B3).
order_items        order_id, product_id, price, quantity, subtotal

---- MONEY LEDGER (added for flexible online payments) -----------
payment_transactions
   Every movement of money on an order is one row here: order_id,
   type (native enum PaymentTransactionType: deposit_paid|
   balance_paid_cash|refund_issued|deposit_forfeited|payout_sent|
   damage_penalty_paid, plus two unused leftovers from an earlier
   design - debt_recorded|debt_recovered), amount, payment_method
   (esewa|cash), status (pending|completed|failed), party (who it's
   for/from: admin|buyer|seller), reference (the eSewa transaction_uuid,
   when relevant), notes. Order helper methods (paidOnline(),
   paidCash(), totalPaid(), remainingAmount()) sum these rather than
   trusting a single status flag. See ESewaExplanation.txt.
payout_requests
   A pending transfer the admin owes to a buyer or seller (a refund, or
   the seller's cut of a forfeited deposit): order_id, recipient_id,
   recipient_role (buyer|seller), purpose (seller_forfeit_share|
   buyer_refund), amount, debt_deducted, esewa_name, esewa_phone,
   qr_image_path, payout_status (awaiting_details|pending|sent|
   settled), details_submitted_at, sent_at. NOTE: the service methods
   to submit these details and mark one sent exist and are tested, but
   no screen calls them yet - see ESewaExplanation.txt section 8 /
   19.1.
seller_debts
   Money a seller still owes the platform, recovered automatically out
   of their next payout: seller_id, related_order_id, amount,
   recovered_amount, reason, status (outstanding|recovered),
   overdue_notified_at, recovered_at. Leftover from an earlier "50%
   compensation" design; only SellerDebtService::recoverFromPayout()
   (deducting debt from a Group 1 forfeit payout) is still called - see
   section 13.

---- DAMAGE PENALTIES AND COMPLAINTS ------------------------------
damage_penalties
   Issued when an admin confirms a Group 2 buyer complaint was genuine
   damage: order_id, seller_id, amount (30% of the order total by
   default), transaction_uuid, status (pending|paid|expired),
   verdict_recorded_at, due_at (7 days later by default), paid_at,
   expired_at, legal_action_flagged, prior_is_auction_allowed,
   prior_is_seller (the seller's access snapshotted before revocation,
   so it can be restored exactly), restored_at, restored_by_admin_id.
seller_damage_strikes
   One row per paid damage penalty: seller_id, order_id,
   damage_penalty_id, amount. Reaching 3 strikes permanently bans the
   seller (see users.is_permanently_banned below).
complaint_messages
   A chat thread between the buyer and any admin about an order whose
   complaint_status is set: order_id, sender_role (admin|buyer),
   sender_id (not a foreign key - it points at admins.id or users.id
   depending on sender_role, the same "loose party tag" pattern as
   payment_transactions.party), body.
seller_warnings
   A lighter-weight caution an admin can issue without a full damage
   verdict: seller_id, admin_id, product_id (nullable - set when issued
   from a specific listing), reason.
users gained: is_permanently_banned, permanent_ban_reason,
   permanently_banned_at (set on a 3rd confirmed-damage strike; a
   permanently banned seller can never have access restored again).

---- MESSAGING / NOTIFICATIONS / AI ------------------------------
conversations      product_id, buyer_id, seller_id, last_message_at
chat_messages      conversation_id, sender_id, body, read_at
notifications      Laravel's bell notifications: id (uuid), type,
                   notifiable_type + notifiable_id (a user OR an
                   admin), data (JSON), read_at
ai_chat_messages   AI assistant chat: user_id (null for guests),
                   session_id, role ('user'|'assistant'), body, is_error

---- FRAMEWORK TABLES --------------------------------------------
cache, cache_locks     database cache and locks (AI answer cache, locks)
jobs, job_batches, failed_jobs   the queue tables (no feature uses the
                                 queue by default)

RELATIONSHIPS IN WORDS
   A user has many products, orders (as buyer and as seller), cart
   items, wishlist items, document images, conversations, bids.
   A category has many sub-categories; a sub-category has many products.
   A product has many images, timelines, and (if auction) ONE auction.
   An auction has ONE traditional_auction rule set and many bids.
   An order has many order_items; an auction order links to its auction.
   A conversation has many chat_messages.
   Deleting a user/product/auction cascades to its children (foreign
   keys are set to delete on cascade), except: orders.auction_id and
   product_timelines.actor_id become NULL instead.

7. MODELS AND THEIR RELATIONSHIPS
=====================================================================
A model is a PHP class for one table (app/Models/).

  User            hasMany: products (as seller), documentImages,
                  wishlists, cartItems, buyerOrders, sellerOrders,
                  buyerConversations, sellerConversations, chatMessages,
                  damagePenalties, warnings.
                  Methods: isActiveStatus(), scopeActive(). The status
                  and gender values are always stored lowercase;
                  gender_label gives "Male"/"Female"/"Other".
                  is_permanently_banned/permanent_ban_reason/
                  permanently_banned_at track a 3-strikes damage ban
                  (section 13, DamagePenaltyService).
  Admin           Separate login model (admin guard). Notifiable.
  Product         belongsTo user (seller) and category (sub-category);
                  hasMany images, proofImages, timelines, cartItems,
                  orderItems, conversations; hasOne auction;
                  belongsToMany wishlistedByUsers.
                  Methods: isDirectSell(), isAuction(),
                  isWishlistedBy(), logTimeline() (writes history),
                  approveListing() (approve product AND activate its
                  auction; sets approval_status=approved),
                  rejectListing($reason) (approval_status=rejected),
                  requestCorrection($reason) (approval_status=
                  correction, with remarks the seller must address
                  before resubmitting), estimated_value,
                  suggested_starting_price, condition_label,
                  status_label.
  ProductImage    belongsTo product; image_type enum.
  ProductTimeline belongsTo product and actor (user).
  Category        hasMany subCategories.
  SubCategory     belongsTo category; hasMany products.
  Auction         belongsTo product and winner; hasOne
                  traditionalAuction; hasMany bids.
                  Methods: isLive(), isUpcoming(), isEnded(),
                  isSettled(), getStepIncrement(), getMinNextBid(),
                  effective_end_time (extended_end_time else end_time).
  TraditionalAuction  belongsTo auction (bid rules).
  Bid             belongsTo auction and bidder.
  Order           belongsTo buyer, seller, auction; hasMany items,
                  transactions (payment_transactions, ordered),
                  payoutRequests, sellerDebts; hasOne damagePenalty;
                  hasMany complaintMessages.
                  Methods: needsDeposit(), acceptsOnlinePayment(),
                  status_label, status_badge, handover_label,
                  payment_method_label, paidOnline(), paidCash(),
                  totalPaid(), remainingAmount(), minimumDeposit()
                  (section 5's payment_transactions ledger, see
                  ESewaExplanation.txt). It creates the order number
                  ORD-YYYYMMDD-XXXXX automatically.
  OrderItem       belongsTo order and product.
  CartItem, Wishlist   belongsTo user and product.
  Conversation    belongsTo product, buyer, seller; hasMany messages;
                  hasParticipant($user).
  ChatMessage     belongsTo conversation and sender.
  DocumentImage   belongsTo user (identity documents).
  Faq, FaqCategory  FAQ content.
  Setting         key/value store: Setting::get('key', default),
                  Setting::set('key', value, group).
  Subscriber      newsletter email.
  AiChatMessage   AI chat rows; scopes forOwner(), sameOwnerAs().
  PaymentTransaction   belongsTo order; casts type/payment_method/
                  status/party to their enums (section 8, section 5's
                  ledger table).
  PayoutRequest   belongsTo order and recipient (a User); casts
                  recipient_role/purpose/payout_status.
  SellerDebt      belongsTo seller (User) and related order.
                  getRemainingAttribute() = amount - recovered_amount.
  DamagePenalty   belongsTo order, seller (User), restoredByAdmin;
                  hasMany strikes (SellerDamageStrike).
                  canBeRestored() gates DamagePenaltyService::
                  restoreAccess().
  SellerDamageStrike   belongsTo seller (User), order, damagePenalty.
  ComplaintMessage     belongsTo order. sender() resolves to an Admin
                  or the order's buyer depending on sender_role, since
                  sender_id isn't a real foreign key (it can point at
                  either table).
  SellerWarning   belongsTo seller (User), admin, and an optional
                  product.
  (Notifications use Laravel's own DatabaseNotification model.)

10. MIDDLEWARE AND GUARDS
=====================================================================
Aliases are registered in bootstrap/app.php.

  user   -> UserMiddleware
            Must be logged in on the "web" guard. If the account status
            is not "active" the user is logged out with the message
            "Your account has been marked inactive by the admin."
  admin  -> AdminMiddleware
            Must be logged in on the separate "admin" guard, else
            redirected to /admin/login.
  auth.otp -> EnsureGoogleSession
            Only lets you reach /verify-otp and /complete-profile when a
            signup/Google session exists (session key google_user); the
            profile step also requires the OTP to be verified first.

Unauthenticated redirects (redirectGuestsTo): URLs starting with
"admin" go to the admin login, everything else to the user login.

Two guards exist (config/auth.php): "web" (users) and "admin". They are
completely separate: an admin is not a user and vice versa.

13. SERVICES (BUSINESS LOGIC)  -  app/Services/
=====================================================================
AuctionEngineService
   The heart of bidding: getStepIncrement (minimum step),
   processBid (manual/proxy bids, anti-sniping, notifications),
   determineWinner (winner, reserve, tie-break, order creation),
   checkAndFinalizeIfExpired (safe settlement), calculateOptimalReserve
   and calculateEquilibriumBid (advisory suggestions).
   See AlgorithmsExplanation.txt.
AuctionValuationService
   Estimated value of a used item (depreciation by age x condition
   factor) and the suggested starting price (80%).
OrderCancellationService
   Cancels an order and decides what happens to money already paid
   online: a Group 1 reason forfeits the minimum deposit (split
   default 80% platform / 20% seller) and refunds any excess; a Group 2
   reason (a complaint) puts the order "under review" and notifies
   admins; recordDamageVerdict() records an admin's confirmed-damaged
   (full refund + DamagePenaltyService::issue()) or not-damaged
   (falls back to the Group 1 rule) verdict. Also relists the product
   when an auction sale falls through. See AlgorithmsExplanation.txt
   section 16.
DamagePenaltyService
   The seller-pays-admin damage penalty lifecycle: penaltyFor()
   (30% of the order total by default), issue() (revokes seller/
   auction access, snapshotting it first so it can be restored
   exactly), notifySeller(), recordPayment() (logs the payment, records
   a SellerDamageStrike, permanently bans the seller on the 3rd
   strike), restoreAccess() (manual admin action; refuses if another
   penalty is unresolved or the seller is banned), expireOverdue()
   (scheduled hourly: deactivates the account and flags legal action
   past the due date). See ESewaExplanation.txt section 8a.
SellerDebtService
   recoverFromPayout() nets a seller's outstanding SellerDebt (oldest
   first) against an admin-held payout before it's sent - only money
   the admin actually holds can be deducted, not cash paid at the
   meetup. This is the only method still called; the debt-creating
   methods this service used to have (record(), penaltyFor(),
   outstandingFor()) were removed once DamagePenaltyService's direct
   penalty replaced that design - seller_debts can still be seeded
   directly (e.g. by a factory in tests) even though nothing creates
   one at runtime any more.
OrderPaymentService
   complete() (seller confirms handover: records the cash balance,
   decrements stock, updates the timeline), submitPayoutDetails() and
   markSent() (the payout hand-off - a recipient supplies their eSewa
   details, an admin marks the real transfer sent). Tested at the
   service layer, but not yet wired to any screen - see
   ESewaExplanation.txt section 8/19.
EsewaPaymentService
   Builds the signed eSewa payment form (shared by the deposit flow and
   the damage-penalty flow), works out a buyer's allowed payment range,
   verifies eSewa's callback and checks the payment status. See
   ESewaExplanation.txt.
AiClientService, AiAssistantPromptService
   Talk to Gemini and build the AI's instructions.
HtmlSanitizerService
   Cleans the rich-text description and specifications before saving
   (removes dangerous HTML) and prepares them for display.
Helper: app/Helper/helper.php (loaded by Composer) has small global
functions such as backedEnumAsArray().

16. SCHEDULER AND BACKGROUND PROCESSES
=====================================================================
   php artisan serve          the web server (development)
   php artisan queue:listen   runs queued jobs (optional: nothing needs
                              it by default; OTP emails and AI replies
                              run inside the web request)
   php artisan reverb:start   the WebSocket server (real time)
   php artisan schedule:work  runs the scheduler:
        routes/console.php -> "finalize-expired-auctions", every minute:
        finds active auctions whose end time has passed and settles them
        (winner or unsold, order creation, notifications).
   npm run dev                Vite dev server
   composer run dev           starts server + queue + Reverb + logs +
                              Vite together (but NOT the scheduler).
Auctions are also settled when someone opens the auction page, when the
countdown reaches zero on an open page, or when someone tries to bid,
so the scheduler is a safety net that guarantees settlement.

19. THE MAIN WORKFLOWS, END TO END
=====================================================================
A) BECOMING A USER
   /register (email) -> /verify-otp (6-digit code by email) ->
   /complete-profile (details, password; can apply as seller) -> logged in.
   Or "Continue with Google" -> same OTP step -> profile -> logged in.

B) BECOMING A SELLER
   User asks (navbar, settings, products page or profile step) ->
   users.seller_application_pending = true, admins notified ->
   admin approves at /admin/seller-requests -> is_seller = true.

C) LISTING A SECOND-HAND PRODUCT
   Seller: /my-products/create/direct-sell -> ManageProduct.save ->
   product status "pending", admins notified -> admin approves at
   /admin/products -> product active and visible.

D) LISTING AN AUCTION
   User applies at /join-auction (documents) -> admin approves ->
   is_auction_allowed = true. Seller: /my-products/create/auction (with
   schedule, starting bid, reserve, increment) -> admin approves ->
   auction becomes "active" and goes live at the start time.

E) BUYING A SECOND-HAND PRODUCT
   Product page -> Buy now / Add to cart -> /checkout -> placeOrder ->
   order per seller, seller notified -> seller confirms in
   /my-orders/{order} -> meetup, inspect, pay cash -> seller marks
   completed. Either side can cancel with a reason.

F) BIDDING AND WINNING
   /auction/{id} -> placeBid -> AuctionEngineService::processBid ->
   price updated, others see it live, previous leader gets an outbid
   notice -> when the time ends the auction is settled (scheduler / page
   / countdown) -> winner and order created, winner and seller
   notified, winner emailed.

G) PAYING FOR THE AUCTION WIN AND HANDOVER
   Winner opens the order -> chooses an amount (at least the minimum
   deposit, at most the full price) -> "Pay via eSewa" ->
   /my-orders/{order}/pay-deposit -> eSewa -> success callback logs a
   payment_transactions row, marks deposit_status "paid" and notifies
   the seller -> "Schedule Meetup" sets the meetup date/time -> meetup,
   any remaining balance in cash, seller marks completed.
   If cancelled after paying: Group 1 reason (seller cancels, or buyer
   cites changed mind/other) settles immediately - refund or a forfeit
   split; Group 2 reason (a complaint) goes to workflow G2 below instead
   of settling right away.

G2) A DAMAGE COMPLAINT
   Buyer cancels citing item_damaged / not_as_described /
   documents_missing -> order goes "under review", every admin is
   notified -> buyer and an admin can message each other in a
   complaint-chat thread on the order page while it's open -> an admin
   physically inspects the item and records a verdict on
   /admin/orders/{order}:
     confirmed damaged -> buyer refunded in full, seller's account
        suspended, a 30% damage penalty issued (due in 7 days) ->
        seller pays it at /my-penalties via eSewa -> a strike is
        recorded (3 strikes permanently bans the seller) -> admin can
        restoreSellerAccess() once paid (refused if another penalty is
        still open or the seller is banned)
     not damaged -> falls back to the Group 1 forfeit-split rule
   An unpaid penalty past its 7-day deadline is caught by the hourly
   scheduled command, which deactivates the seller's account and flags
   the order for admins as needing legal/manual action.

H) CHATTING
   Product page -> "Message Product Owner" -> conversation created ->
   messages appear live on both sides and as bell notifications; the
   full inbox is /messages.

I) ADMIN OVERSIGHT
   Dashboard counts and two alert sections (overdue penalties, open
   complaints), seller/auction/product approvals (including reject and
   request-correction, both notifying the seller), user status and
   warnings, categories and FAQs, all orders (with an open-complaints
   filter) and detail pages, and site settings.

21. KNOWN LIMITATIONS
=====================================================================
   - eSewa runs against eSewa's SANDBOX only, and only for auction-win
     online payments and damage-penalty payments. Second-hand orders
     are cash on meetup only.
   - Refunds and payouts are recorded as PayoutRequest rows and paid
     back manually outside the app - and right now there isn't even an
     on-screen way to submit payout details or mark one sent (the
     service methods exist and are tested; no button calls them yet).
     See ESewaExplanation.txt section 8/19.
   - Gemini models can be overloaded or retired; the AI uses fallback
     models and shows a clear message if all fail.
   - The scheduler must be running for auctions to be settled with
     nobody looking at them; the same is true of the hourly overdue-
     damage-penalty check.
   - No "stale order" automation exists yet (an admin check for meetup
     dates that have passed with the order never completed/cancelled).
     This was planned but never built - see newUpate.txt Part B3.
   - Change the default admin password and set APP_DEBUG=false before
     any public deployment.
   - Some older leftovers exist: orders.shipping_address,
     products.delivery_available and the "delivery" handover value are
     kept only so old data still displays; two PaymentTransactionType
     cases (debt_recorded, debt_recovered) and two config keys
     (ESEWA_SELLER_PENALTY_PERCENTAGE, SELLER_DEBT_OVERDUE_DAYS) are
     similar leftovers from an earlier "50% seller debt" design that
     DamagePenaltyService replaced; AuctionStatus::ENDED is accepted by
     the model's isEnded()/isSettled() helpers but is never actually
     written.
